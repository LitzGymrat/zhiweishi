# 校园PoC现场实施与数据采集手册

## 一、本文用途

本文是 [10_poc_execution_plan.md](10_poc_execution_plan.md) 的现场实施补充版。

这份文档只关注三件事：

1. 当天怎么组织 PoC。
2. 现场怎么采原始数据。
3. 采完后怎么整理成后续可用于 judge、PPT 和介绍材料的原始包。

本文不重复展开评分规则、judge 字段和结论写法；这些内容统一以 [10_poc_execution_plan.md](10_poc_execution_plan.md) 为准。

## 二、适用范围

本手册默认适用于下面这种场景：

1. 校园环境。
2. 1 个下午内完成。
3. 4 名测试者。
4. 2 个必做 PoC。
5. Streamlit 原型已可运行，知识库已提前建好。

如果当天人数、场地或设备条件略有变化，也尽量不要改动核心流程，只调整轮次安排和分工。

## 三、当天目标

当天执行结束后，至少要拿到下面 4 类原始材料：

1. PoC 一计时与任务总表。
2. PoC 一答案卡原件或转录文本。
3. PoC 二回写前后截图和样本处置记录。
4. 可直接送入 LLM-as-judge 的输入包。

只要这 4 类材料拿齐，后续评分、汇总和做 PPT 就不会缺底稿。

这里先说清楚两点：

1. 真正需要组织测试者、控场、计时的核心部分，是 PoC 一。
2. PoC 二本质上是一次内部复核式演示验证，可以由项目组自己完成，不需要再额外组织一轮参与者。

## 四、角色分工

### 1. 最小分工配置

如果两个 PoC 放在一起做，现场建议至少有下面 4 类角色：

1. 主持人：负责宣讲规则、发放任务卡、控制节奏。
2. 计时记录员：负责计时、记第一次定位到依据的时间、维护总表。
3. 技术保障员：负责原型页面、浏览器、知识库、截图、备份与恢复。
4. 测试者：4 人，按既定矩阵完成任务。

如果人手不足，主持人和技术保障员可以由同一人兼任，但计时记录员最好不要兼岗。

如果只看 PoC 二，则不需要这套完整配置。PoC 二最小只需要：

1. 1 名操作人。
2. 1 名复核人。

也就是说，PoC 二可以由你们项目组自己提前做完，正式现场重点放在 PoC 一。

### 2. 各角色当天必须完成的事

#### 主持人

1. 核对到场人员并分配测试者编号。
2. 宣讲统一规则。
3. 发放任务卡和答案卡。
4. 每轮开始和结束时统一口令。
5. 确保测试者不互相讨论、不互看答案。

#### 计时记录员

1. 维护 PoC 一记录总表。
2. 为每个任务记录开始时间。
3. 记录测试者第一次明确指出有效依据的时间。
4. 记录超时、卡住、异常中断等情况。
5. 回收答案卡并核对编号是否完整。

#### 技术保障员

1. 提前启动原型并检查可用性。
2. 确认页面、模型、知识库和默认参数一致。
3. 负责 PoC 二的知识库备份与恢复。
4. 负责保存截图、整理文件路径和归档目录。
5. 活动结束后整理 judge 输入文件。

#### 测试者

1. 按任务卡完成指定模式任务。
2. 只填写统一答案卡，不额外提交自由发挥版答案。
3. 第一次定位到依据时必须立即举手或口头示意。
4. 不得与其他测试者交流。

## 五、会前准备清单

### 1. 前一天必须完成的准备

前一天建议完成下面 8 项：

1. 确认原型可运行，且使用的是固定 URL。
2. 重新建库一次，保证知识库状态最新且一致。
3. 备份 `prototype/data/documents/case_cards/`、`prototype/data/chroma_db/` 和 `prototype/data/bm25_index.json`。
4. 打印或导出任务卡、答案卡、计时总表。
5. 为 4 个任务各准备 1 张任务参考卡。
6. 确认浏览器、网络、电源、投屏设备正常。
7. 准备一个统一的数据归档目录。
8. 提前演练一遍 PoC 二回写流程，确认不会把不完整案例写入正式演示环境。

### 2. 建议使用的归档目录

建议在项目内单独建一个 PoC 数据目录，方便后续 judge 和材料整理。推荐结构如下：

```text
prototype/data/poc_runs/20260418_campus_poc/
  01_admin/
    participants.csv
    task_assignment.csv
    task_reference_cards/
  02_poc1_raw/
    answer_cards/
    time_log.csv
    transcribed_answers/
    judge_input.jsonl
    judge_output.jsonl
  03_poc2_raw/
    screenshots/
    writeback_record.md
    backup_note.txt
  04_summary/
    result_table.csv
    ppt_summary.md
```

如果你们嫌目录太多，最少也要分出 `poc1_raw`、`poc2_raw` 和 `summary` 三层。

### 3. 建议准备的纸质或电子材料

当天建议至少准备下面这些：

1. 测试者签到表。
2. 任务分配表。
3. 任务卡。
4. 答案卡。
5. PoC 一计时总表。
6. PoC 二截图清单。
7. 样本处置记录模板。

## 六、统一实验条件

为了让数据可比，当天所有测试都要锁定下列条件：

1. 使用同一个原型版本。
2. 使用同一个知识库版本。
3. 使用同一个页面 URL。
4. 使用同一批任务卡。
5. 使用同一个答案卡模板。
6. 系统辅助模式下，不允许测试者自行修改页面参数。
7. 人工模式下，不允许测试者查看原型输出。

建议当天明确宣布下面 4 条规则：

1. 不允许修改“检索片段数量”等系统参数。
2. 不允许切换到无关标签页。
3. 不允许上传新文档。
4. 不允许测试者之间口头交流。

## 七、现场布置建议

### 1. 座位安排

建议采用下面的布置：

1. 4 名测试者分散落座，避免互相看到屏幕。
2. 主持人和计时记录员坐在前方，能看到所有测试者。
3. 技术保障员坐在主持人旁边，单独操作主控电脑。
4. 投屏屏幕只展示规则和开始/停止提示，不展示任何答案内容。

### 2. 网络与设备要求

建议现场满足下面条件：

1. 主持人电脑必须能稳定打开原型页面。
2. 测试者电脑浏览器提前打开到指定页面。
3. 所有设备尽量接同一局域网。
4. 现场备一台备用电脑，以防某位测试者设备突然异常。

## 八、测试者编号与基础信息采集

为了后续说明“至少一半测试者不是项目核心成员”，建议签到时只采最少信息，不做长问卷。

建议签到表只留下面 4 列：

| 字段 | 用途 |
| --- | --- |
| 测试者编号 | 后续所有记录统一引用 |
| 专业或背景 | 说明样本构成 |
| 是否项目核心成员 | 支撑可信度说明 |
| 是否有设备/实验室相关经历 | 作为补充背景 |

除了这 4 列，不再收集更多个人信息。

## 九、PoC一现场执行SOP

### 0. 先说结论：PoC一最简怎么跑

如果你们只想先抓住主干，可以直接按下面这 8 步执行：

1. 让 4 名测试者坐好，发编号、任务卡和答案卡。
2. 主持人宣布规则：每人两轮，每轮 8 分钟，找到第一条依据要立刻示意。
3. 跑第 1 轮，计时员只做两件事：开表、记“第一次依据定位时间”。
4. 8 分钟到，立刻收答案卡。
5. 切换任务和模式，跑第 2 轮。
6. 再次收答案卡。
7. 当场拍照、转录、整理成 judge 输入。
8. 当天导出一张总表和 judge 输出结果。

如果按这 8 步能完整跑通，PoC 一就已经成立。下面的内容，是把这 8 步展开成可直接照着执行的版本。

### 1. 任务分发前说明

正式开始前，主持人需要统一说明下面 5 条：

1. 每人共做 2 个任务。
2. 每个任务 8 分钟。
3. 第一次找到有效依据时要立刻举手或说“找到依据”。
4. 所有答案只写在统一答案卡上。
5. 超时后必须立即停止，不得继续补写。

建议主持人直接照下面这段话念：

“今天每人做两轮任务，每轮 8 分钟。人工模式只能查资料，系统模式可以看原型输出。你第一次找到准备采用的依据时，请立刻举手或说‘找到依据’，我们只记第一次。时间到后必须立即停笔，所有答案只写在答案卡上。”

### 2. 每轮执行动作

PoC 一每轮都按下面动作执行：

1. 主持人口头宣布“开始”。
2. 计时记录员为本轮所有测试者同时启动计时。
3. 测试者独立完成任务。
4. 测试者第一次定位到依据时举手或口头示意。
5. 计时记录员记下该测试者的首次依据定位时间。
6. 8 分钟到时，主持人口头宣布“停止”。
7. 计时记录员和主持人立即回收答案卡。

为了现场更稳，建议把每轮动作压成统一口令：

1. 主持人说“准备”。
2. 计时记录员确认所有人拿到正确任务卡。
3. 主持人说“开始”。
4. 测试者作答。
5. 有人示意“找到依据”时，计时员记时。
6. 主持人说“还有 1 分钟”。
7. 8 分钟到，主持人说“停止，放下笔和键盘”。
8. 收卷。

如果现场只想极简执行，就死守这套口令，不再临场发挥。

### 3. 第一次依据定位时间的统一判定

为了减少争议，统一按下面规则记时：

1. 人工模式下：测试者明确指出第一条可用文档时记时。
2. 系统模式下：测试者明确指出第一条准备采用的依据文档时记时。
3. 只要测试者没有明确示意，就不主动替他记时。
4. 如果测试者说了多个来源，按他第一次明确说出的那条记时。

### 4. 答案卡回收后立即做的事

每轮结束后，建议当场完成下面 4 件事：

1. 检查每张答案卡是否写了测试者编号、任务编号、模式。
2. 用手机拍照或扫描成电子版。
3. 用统一文件名保存。
4. 把关键内容转录到文本文件，便于后续送入 judge。

这里的关键点是：

不要等活动结束后再统一处理答案卡。每轮收完就拍、就命名、就归档，否则后面最容易乱。

推荐命名方式：

```text
P1_T1_manual_answer.jpg
P1_T1_manual_answer.txt
P2_T3_system_answer.jpg
P2_T3_system_answer.txt
```

### 5. PoC一当天必须留下的原始数据

PoC 一当天必须至少留下下面 5 类原始数据：

1. `participants.csv`：测试者编号和基础背景。
2. `task_assignment.csv`：每个人对应哪个任务、哪种模式。
3. `time_log.csv`：首次依据定位时间。
4. `answer_cards/`：答案卡图片或 PDF。
5. `transcribed_answers/`：答案卡文字转录版。

如果你们当天非常赶，最低也要保证下面 3 样不丢：

1. `time_log.csv`
2. `answer_cards/`
3. `transcribed_answers/`

这 3 样是后续 judge 和汇总的底线。

### 6. PoC一推荐数据总表字段

建议 `time_log.csv` 或主总表至少包含下面字段：

| 字段 | 说明 |
| --- | --- |
| participant_id | 如 P1 |
| task_id | 如 T1 |
| device_type | 液压泵站 / 数控主轴单元 |
| mode | manual / system |
| start_time | 开始时间 |
| first_evidence_time | 第一次依据定位时间 |
| first_evidence_elapsed_s | 从开始到定位依据的秒数 |
| answer_text_path | 转录答案路径 |
| answer_image_path | 原始图片路径 |
| note | 是否超时、是否卡住 |

这里不直接写分数；评分结果后处理进入 judge 文件。

## 十、PoC二现场执行SOP

### 0. 先说结论：PoC二可以自己做

PoC 二不需要再组织一批测试者。

最实用的安排是：

1. 把 PoC 二当作项目组内部验证。
2. 可以放在 PoC 一之前单独做完。
3. 也可以放在 PoC 一结束后，由你们自己现场完成。

它更像“内部可复现实验”，不是“多人参与式测试”。

### 1. PoC二开始前必须完成的动作

PoC 二开始前，技术保障员必须先做下面 3 步：

1. 备份案例卡目录和索引文件。
2. 确认要做回写的任务编号。
3. 确认本次回写使用 `POC_` 前缀命名。

### 2. PoC二当天执行顺序

PoC 二建议严格按下面顺序执行：

1. 输入回写前问题并截图。
2. 项目组根据模板补全样本处置记录。
3. 由 2 人完成回写前审核。
4. 执行案例回写并更新索引。
5. 打开新生成案例卡并截图。
6. 对同类或相近问题再次提问并截图。
7. 记录新案例文件名和生成路径。

### 3. PoC二必须保留的原始数据

PoC 二必须保留下列文件：

1. 回写前问题截图。
2. 样本处置记录文本或截图。
3. 新生成案例卡截图。
4. 回写后二次提问命中新案例的截图。
5. 一个简短的 `backup_note.txt`，写明备份目录和是否已恢复。

推荐命名方式：

```text
poc2_before_question.png
poc2_writeback_record.md
poc2_generated_case.png
poc2_after_retrieval.png
backup_note.txt
```

## 十一、LLM-as-judge 输入包整理方式

虽然评分规则不在本文展开，但现场数据采完后，最好当天就把 judge 输入整理好，避免后面回忆不清。

建议每条 judge 输入至少包含下面 5 项：

1. 任务编号。
2. 任务描述。
3. 任务参考卡内容。
4. 测试者答案文本。
5. 模式标签。

推荐按 JSONL 保存，每行一条样本。示例结构如下：

```json
{
  "sample_id": "P1_T1_manual",
  "task_id": "T1",
  "mode": "manual",
  "task_prompt": "液压泵站压力波动且伴随异响。",
  "reference_card": {
    "allowed_sources": ["液压泵站维护手册_整理版.md", "液压泵站点检SOP.md"],
    "required_actions": ["检查油位", "检查吸油接头", "检查滤芯状态"],
    "risk_boundary": "不建议继续高负荷试运行"
  },
  "answer": {
    "key_evidence": ["液压泵站维护手册_整理版.md"],
    "steps": ["检查油位", "检查吸油接头", "检查滤芯状态"],
    "risk_note": "先低负荷排查，不要继续高负荷运行"
  }
}
```

## 十二、当天时间表建议

如果要在一个下午内跑完，建议采用下面这个时间表：

| 时间段 | 动作 |
| --- | --- |
| 00:00 - 00:10 | 签到、编号、规则说明 |
| 00:10 - 00:18 | PoC 一第 1 轮 |
| 00:18 - 00:20 | 回收答案卡、切换 |
| 00:20 - 00:28 | PoC 一第 2 轮 |
| 00:28 - 00:45 | 拍照、转录、整理 time log 和 judge 输入 |
| 00:45 - 01:10 | PoC 二回写前提问、审核、回写 |
| 01:10 - 01:20 | 回写后二次检索和截图 |
| 01:20 - 01:40 | 跑 judge、导出结果、归档文件 |

如果 judge 当天来不及跑，至少也要把 judge 输入包整理出来。

## 十三、现场异常处理

### 1. 原型页面打不开

处理顺序：

1. 技术保障员先刷新本地页面。
2. 确认 Streamlit 服务是否仍在运行。
3. 如果 5 分钟内无法恢复，当天只保留人工模式数据，并记录异常原因。

### 2. 模型调用异常

如果系统辅助模式还能基于检索给出兜底结果，可以继续执行；但要在总表备注中标明“本轮为兜底模式”。

### 3. 测试者未按规则示意首次依据定位

如果测试者没有明确举手或口头示意，就不补记该时间，统一记为空值并在备注写明“未示意”。

### 4. 任务超时

超时后必须立刻收卷，不允许补答；备注栏写“timeout”。

## 十四、活动结束后的整理动作

当天结束前，建议务必完成下面 6 件事：

1. 检查 8 份答案卡是否齐全。
2. 检查 4 张 PoC 二关键截图是否齐全。
3. 检查主总表是否没有缺失编号。
4. 检查 judge 输入包是否能对应到每一条答案。
5. 导出一份 PPT 可用的汇总表。
6. 如果 PoC 二污染了正式知识库，恢复备份。

## 十五、最终应交给材料整理人的文件

现场执行结束后，建议把下面这些直接交给后续做 PPT 的同学：

1. `result_table.csv`：汇总表。
2. `judge_output.jsonl`：judge 原始输出。
3. `poc2` 截图包。
4. 一段 100 到 150 字的验证结论底稿。

这样后续做材料的人不用再回头找现场记录。
