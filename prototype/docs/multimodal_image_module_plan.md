# 图像证据模块实施计划

## 当前实现状态

首版已实现阶段 A 与阶段 B 的基础链路：案例回写页面可上传 JPEG/PNG；系统执行格式、大小、像素和 EXIF 清理校验后，以随机 `image_id`、SHA-256 和案例目录保存原图。配置 OpenAI-compatible `vision_*` 接口后，系统会抽取 OCR、图像说明、可见观察及不可判读项；未配置时只归档原图并明确标记“未抽取”。

派生结果会写进案例卡，因此由现有文本向量检索和 BM25 检索；后续命中案例时，排障页会显示原图。视觉抽取结果被明确标为派生证据，不能确认根因、替代现场复核或触发高风险动作。实时图片辅助排障和图文联合向量检索仍属于后续阶段。

## 目标与边界

首轮文本 SFT+LoRA 已完成。图像模块的目标不是让模型仅凭一张照片确认故障或下达处置指令，而是把现场图片转成可检索、可回溯、可人工核验的案例证据，并与既有 SOP、维修记录和案例卡共同支撑辅助排查。

图像模块在每次回答中必须区分三类信息：原图可见事实、OCR/视觉抽取的派生文本、基于这些证据的保守排查假设。无法确认、画面模糊、遮挡或缺少关键角度时，模型必须明确要求人工补拍或现场复核。

## 目标流程

```text
现场上传图片
  -> 格式、尺寸、病毒与隐私检查
  -> 原图对象存储 + SHA-256 + 案例/设备关联
  -> OCR、图像说明、可见异常抽取
  -> 生成带 image_id 与区域引用的证据文本
  -> 写入案例卡并进入文本向量检索 + BM25
  -> 检索命中后展示原图、证据文本与来源
  -> 仅在需要时由视觉模型对关键原图和文本上下文共同复核
  -> 人工确认处置，结果回写为案例
```

第一版优先采用“图片文本化后进入现有混合检索”的方式，不引入单独的图像向量库。这样可以复用当前 RAG、审计和案例回写链路，且每项建议都有可阅读的证据文本。积累足够经审核图像案例后，再评估图文联合向量检索。

## 模块拆分

| 模块 | 首版职责 | 关键边界 |
| --- | --- | --- |
| 图片上传与存储 | 接收 JPEG/PNG，生成 `image_id`、SHA-256、时间、设备和案例关联；保存原图与缩略图 | 保留原图；禁止以文件名或用户描述替代来源标识 |
| 预处理 | 限制大小/分辨率，纠正方向，移除不需要的 EXIF，进行恶意文件检查 | 不对原图做会改变缺陷外观的增强后覆盖 |
| 视觉抽取 | 输出 OCR、图像说明、可见部件/异常、不可判读项及置信提示 | 只能描述可见内容；不得直接输出根因、维修指令或“已确认损坏” |
| 证据归档 | 将抽取结果写为带 `image_id`、页/区域和模型版本的案例证据文本 | 派生文本不是 SOP 或现场结论，必须保留原图回链 |
| 检索与生成 | 以证据文本参与现有 BM25/向量检索，回答中返回图片来源和不确定性 | 图片未命中时不能编造视觉证据；高风险动作仍须遵守现有安全门禁 |
| 人工审核与回写 | 现场人员确认图中现象、处置结果和是否可复用 | 人工结论与模型抽取分别存储，不能互相覆盖 |

## 图片证据契约

每张图片至少保存以下可审计字段；原图路径或对象存储地址不进入模型训练语料。

```json
{
  "image_id": "IMG-20260622-0001",
  "case_id": "CASE-...",
  "equipment_id": "EQ-...",
  "sha256": "...",
  "captured_at": "2026-06-22T10:30:00+08:00",
  "storage_ref": "private-object-reference",
  "ocr_text": "...",
  "image_summary": "控制柜端子排局部照片，标签可见...",
  "observable_findings": [
    {
      "region": "右上角端子排",
      "observation": "可见线缆绝缘层磨损，是否露芯无法从该角度确认",
      "confidence": "medium"
    }
  ],
  "unreadable_or_missing": ["铭牌被遮挡", "未提供整体接线环境"],
  "extractor": {"model": "vision-model-id", "version": "..."},
  "review_status": "pending_human_review"
}
```

`observable_findings` 只写可见现象，不写“接触不良”“轴承损坏”等根因。任何图像区域标记、裁剪图和 OCR 结果都必须能回到同一 `image_id` 的原图。

## 分阶段交付

### 阶段 A：可审计上传与展示

1. 在故障排查和案例回写页面增加图片上传、预览、删除和设备/案例关联。
2. 支持 JPEG/PNG、文件大小和分辨率限制、EXIF 最小化处理，以及原图 SHA-256。
3. 案例卡展示缩略图、原图链接和拍摄时间；未上传图片时文本链路行为不变。
4. 完成权限、保留期限和人工删除流程，避免现场照片无边界留存。

### 阶段 B：OCR 与可见异常文本化

1. 使用视觉能力模型抽取 OCR、图像说明、可见异常和不可判读项，输出严格 JSON。
2. 将派生结果作为 `image_evidence` 写入案例卡并进入现有混合检索；检索结果显示“图片派生证据”标签。
3. 回答中若引用图片，返回 `image_id`、可见事实和原图入口；不能把视觉模型的推测表述为现场确认。
4. 先以异步队列处理，上传成功不等待视觉抽取完成；失败可重试并保留失败原因。

### 阶段 C：关键图像复核与受控多模态问答

1. 仅将检索命中的少量关键原图和对应文本上下文发送给视觉模型复核，设置图片数量、分辨率和超时上限。
2. 复核输出仍遵循现有 `fault_diagnosis` JSON 契约，并增加图片证据来源字段；无充分图像证据时回退文本 RAG 答案。
3. 由人工确认图片现象和最终处置后，形成可复用案例；未经审核的图像描述不得直接进入训练集。

## 验收与评测

单独建立不参与训练的图像评测集，至少覆盖：清晰正常、典型可见异常、模糊/遮挡、OCR 误读、设备不匹配和文本证据与图片冲突。

首版验收指标：

- 每条图片派生证据能回链到原图、模型版本和案例/设备 ID。
- OCR 与可见异常结果可由人工复核；低置信或不可判读项必须明确呈现。
- 文字检索结果可召回相关图片证据，且界面能显示其来源。
- 图片缺失、模糊或与文本冲突时，系统不会给出确定根因、拆检、更换或调参指令。
- 与纯文本基线相比，图像加入后应分别报告检索命中、结构化契约、证据边界、安全越界和人工复核通过率；不只报告“看图准确率”。

## 暂不纳入首版的内容

- 不从互联网图片或未经授权的现场照片直接构建训练集。
- 不以视觉模型输出替代维修人员的安全确认和最终结论。
- 不在第一版就引入大规模图像向量数据库、端到端多模态微调或自动工单执行。

这些限制确保图像能力先成为现有 RAG 闭环中的一类受控证据，再逐步扩大为多模态案例能力。
